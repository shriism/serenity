# Serenity architecture

## Runtime boundaries

- **Renderer (`src/renderer/`)** presents the workspace. It has no Node.js filesystem access or direct provider credentials.
- **Preload (`src/preload/`)** exposes a deliberately small, typed API through Electron's context bridge.
- **Main process (`src/main/`)** chooses the workspace, validates edits, loads files, indexes content, and runs AI SDKs. Provider credentials use OS-protected storage outside the workspace when available, or remain in memory for that app session.
- **Shared (`src/shared/`)** defines record types and the module registry.

Agent SDK tools are disabled or read-only. Providers return proposed knowledge; Serenity performs writes after the selected workflow's review or autonomy rule. Conversations, proposal decisions, claim sources, and merge history are independent of provider-private sessions. User-initiated conversation requests use a cancellable signal across the provider adapters. Every provider request writes a record under `activity/` with its operation, provider, referenced workspace IDs, prompt size/checksum, and outcome; raw prompts and credentials are not duplicated there.

Autonomy and read scope are stored with each conversation. The default autonomous permission set allows claims only; entity, task, and event writes can be enabled independently for that workflow. Even when entity writes are enabled, creating a new category or resolving a potentially ambiguous identity remains a review action. The default read scope is the full chosen workspace. In selected mode, only chosen entities and their claims, chosen documents, and specifically allowed conversation/module records are eligible for transmission. Selection is enforced when assembling context and again when accepting proposed writes to existing entities.

When a workspace does not fit a provider request, the knowledge engine retrieves from its full local index, sends an explicit catalog and relevant excerpts, and can supply a requested second excerpt. Each conversation message records the references, byte counts, excerpt offsets, and checksums sent to the provider. Retrieval selects context for transmission; it does not change which workspace files are available to the human or to later AI retrieval.

## Source of truth

The chosen directory contains Markdown pages and entities, YAML claims and conversations, imported documents, and YAML data for optional calendar and task modules. Imported documents are copied into `documents/`; the source path is never stored as the document location. Workspace-owned directories must be actual directories, and symlinked record/document/page files are not read as workspace content. `.serenity/index.sqlite` is a rebuildable text index; a damaged copy is set aside and regenerated from knowledge files. `.serenity/semantic-index.yaml` is a rebuildable AI-generated summary and topic-term index, enabled only by an explicit module setting; sparse topic-vector similarity can be computed locally from it. An archived merge preserves the duplicate's Markdown under `archive/entities/` and records its redirect under `archive/merges/`; claims remain in their original files and resolve through that redirect on read. Undoing the merge restores the entity ID and stores the reversed merge under `archive/merges/history/`, so its original claims and links become distinct again without erasing the decision history.

Record IDs are stable UUIDs. Types and relationship names are ordinary user-chosen strings, not a fixed ontology. Sourced claims keep confirmations, conflicts, and retractions distinct. Current-answer choices are append-only records under `resolutions/`, so selecting or undoing a correction does not rewrite its original claims. Edits to a known field update YAML nodes without dropping unknown fields or comments. A stale editor save fails rather than silently replacing an entity, event, task, or conversation changed on disk.

The renderer reports unsaved entity and page edits to the main process, which asks before closing or switching workspaces. Only the current workspace path can be revealed in the OS file manager; the renderer cannot pass arbitrary paths to that operation.

## Resources, commands, and authored pages

`src/shared/resources.ts` gives file-backed and computed workspace items stable `serenity:kind/id` references. A resource is an addressable handle, not a claim that every kind shares one storage schema. The renderer's named command contributions in `src/renderer/src/commands.ts` drive navigation, the command palette, and common actions. The main process continues to validate persistent edits through typed IPC; the command registry is a UI foundation, not an unrestricted execution API. Each contribution carries its own `run` handler against a small `CommandHost` interface the shell implements, plus an optional default chord. `src/shared/keybindings.ts` normalizes chords and merges defaults with an optional workspace `keybindings` map from `.serenity/workbench.yaml`; the main process validates the map's shape, and the renderer reports unknown command IDs and conflicts. Keybindings can only name registered commands, never executable code. `.serenity/session.yaml` stores the last open resource URIs and active view as workspace-local UI state, separate from authored knowledge. References are validated against current resources when restored.

The central workbench resolves built-in views through `src/renderer/src/view-registry.ts` and contributions in `src/renderer/src/builtin-views.tsx`. The knowledge view owns its presentation in `knowledge-view.tsx`; the main shell supplies state and validated operations through a typed context. The registry is also the authority for whether a view is available, so a disabled module's view cannot render or be restored from session state. This registry enables composable internal views, while an installed third-party extension host remains a separate future layer. `src/renderer/src/resource-routing.ts` decides how an addressable resource is presented: entities, extractable documents, and non-Home pages open as restorable tabs in their default view; tasks and events focus their module view; claims open their subject entity; unextractable documents open natively. Routing consults view availability, so session restore, page links, search, and external deletions share one rule for what can still be opened.

The initial `pages/Home.md` is seeded only if it does not exist. Pages have YAML frontmatter, a revision-checked Markdown body, and resource/command links. Fenced `serenity-query` blocks contain bounded YAML selections against the current workspace snapshot; they cannot execute JavaScript or read arbitrary paths. `.serenity/workbench.yaml` selects the Home page and lists navigation groups and command IDs. Both files are user-owned: external edits are watched, not overwritten by a fixed React Home view. Invalid page or workbench YAML is reported in the workspace snapshot. Pages in the default workspace read scope can be supplied as AI context; selected read scope does not silently add them.

## Modules

The registry in `src/shared/modules.ts` describes disableable modules. The workspace records their switches in `.serenity/modules.yaml`. A disabled module retains its files but does not expose its view, accept new writes, or send its records to AI. Calendar and tasks link to existing entities by ID rather than keeping duplicate copies of people and projects. Removed tasks and events are archived under `archive/tasks/` and `archive/calendar/` and can be restored; user edits to active module records are checked against their file revision before archiving.

The file watcher observes workspace records, `pages/`, and the editable background-AI and workbench settings files, but ignores derived indexes and provider-activity writes to avoid indexing loops. Disabling a background module or changing its provider cancels in-flight work before starting more requests.

To add a built-in module, register its ID and description, define its on-disk records and validation, provide main-process operations through the typed preload API, and contribute named UI commands and a view. Keep optional modules separate from the core entity/claim source of truth. Module data must remain intact when the module is disabled. Arbitrary extension loading, user-defined command implementations, and general pane composition are future architecture layers; a YAML menu entry alone cannot provide executable behavior.

## Development verification

`npm test` checks storage invariants and module behavior; `npm run smoke:desktop` boots Electron with an explicitly chosen temporary workspace and exercises the renderer/preload/main-process path. The smoke test can also target a packaged executable and, with a configured account, run a live provider turn. GitHub Actions typechecks, tests, and packages on macOS, Windows, and Linux. Live provider calls require provider-specific credentials and are not made in CI.

Installer icons are generated at package time from the checked-in vector source `assets/icon.svg`; derived PNG, ICO, and ICNS files are not stored in Git.
